# Release Notes - Category Page Performance, Design Setting, Checkout Hardening

**Date:** October 1, 2026
**Version:** 0.2.0
**Type:** Bug Fix / Performance / Feature
**Ticket:** LMM-146, LMM-150

---

## Overview

This release is the Hyvä half of the LMM-146 category page performance work. On Hyvä listings the installment box resolved the Leanpay category promotion separately for every product card, which meant one database lookup per card. The promotion data is now loaded once per listing.

The release also includes LMM-150: the installment widget design is now chosen in admin, and the widget is more robust inside Hyvä Checkout. See [Design Setting and Checkout Hardening (LMM-150)](#design-setting-and-checkout-hardening-lmm-150). **The product page widget changes from Narrow to Default** unless Narrow is selected in admin.

Requires **leanpay/payment 0.17.0 or newer**, which provides the batched loading and the design setting this module calls into.

---

## Problem Statement

Hyvä renders each product card through `Hyva\Theme\ViewModel\ProductListItem`, and this module appends the installment box per card via `afterGetProductPriceHtml()`. Every box resolved the category promotion on its own, so the payment module ran a `catalog_category_product` lookup and a category collection load once per card, with no memoisation.

Hyvä's own product list item block cache masked this on repeat views, which is why the cost was easy to miss: only cards not already cached did the work. A cold cache, a cache flush, a new deploy or a products-per-page change paid the full price.

---

## What's Fixed

### Listing preload

A `beforeGetItemHtml()` plugin on `Hyva\Theme\ViewModel\ProductListItem` calls the payment module's `preloadCategoryPromotions()` once, using the parent block's already loaded product collection. This covers the Hyvä category grid, search results and product widgets.

The query count for the category promotion no longer scales with the number of cards on the page.

### Compatibility guard

The preload lives in `Leanpay_Payment`, and the two modules are released and deployed independently. When paired with a payment module that predates the method, this module now skips the preload and falls back to the previous per-card behaviour, instead of failing the page render with:

```
Call to undefined method Leanpay\Payment\Helper\Data::preloadCategoryPromotions()
```

The composer constraint has also been raised from `>=0.15.0` to `>=0.17.0`, so composer installs refuse the broken combination outright. The runtime guard remains for installations that manage these modules as git submodules, where composer constraints are not enforced.

---

## Measured Impact

Measured on the standard staging environment with the equivalent payment module change, against the same category page, with a full cache flush before every request, on a `leanpay_installment` table of 263,953 rows:

| Products shown | Response before | Response after |
|---|---|---|
| 12 | 1.62 s | 0.67 s |
| 24 | 2.75 s | 0.81 s |
| 36 | 3.81 s | 0.99 s |

Category promotion lookups went from one per card to one per page at every page size.

Most of that gain comes from the payment module changes in 0.17.0. This module's contribution is making the preload happen on Hyvä listings, which would otherwise keep the per-card pattern.

## Technical Details

### Affected Components

- `Plugin/ViewModel/ProductListItemPlugin.php` - added `beforeGetItemHtml()`, which preloads from the parent block's loaded collection, with a guard for older payment module versions
- `composer.json` - version 0.2.0; `leanpay/payment` constraint raised to `>=0.17.0`

### Upgrade Notes

- Upgrade `leanpay/payment` to 0.17.0 or newer at the same time. With an older payment module this module runs correctly but without the performance benefit.
- Installations that track these modules as git submodules should confirm both submodules point at compatible versions, since composer constraints are not applied in that setup.
- The LMM-146 changes require no configuration changes. See the LMM-150 upgrade notes below for the design setting.

- No changes to the rendered installment box, calculated amounts or tooltips

## Testing Recommendations (LMM-146)

1. Hyvä category page with 12 or more products in a category that has a Leanpay promotion: the box renders on every card with the same financing product as before
2. With a query log or profiler and a cold cache, confirm one category promotion lookup per page rather than one per card
3. Flush the cache before each measurement. Hyvä's product list item block cache hides the per-card cost on repeat views, so a warm cache will show no difference either way
4. Hyvä search results page: boxes render and are batched
5. Hyvä home page or CMS product widget: boxes render and are batched
6. Product page and Hyvä checkout: unchanged
7. Pair deliberately with a payment module older than 0.17.0: listings must still render, without the preload, and without a fatal error

## Design Setting and Checkout Hardening (LMM-150)

### Problem Statement

#### 1. The design could only be changed with a layout override

`view/frontend/layout/hyva_catalog_product_view.xml` hardcoded `installment_design` to `narrow` on the product page. Stores wanting the full widget, with the calculator opening below it, had to maintain a layout override in their theme.

#### 2. The product page switched design after a price change

Only the initial product page render received the `narrow` argument. The HTML swapped in when the price changes (configurable options, custom options, the `leanpay/installment/index` endpoint) and the checkout widget were rendered without it and fell back to `default`. On a narrow product page, selecting an option could switch the widget to the default design.

#### 3. Checkout re-renders reset the calculator

The widget root carried `wire:key="<?= uniqid() ?>"`, which changed on every render. Inside Hyvä Checkout, every Magewire re-render of the payment method therefore replaced the Alpine component, closing the calculator. Re-renders happen on shipping method changes and checkout autosave, so on a one-step checkout the calculator could close immediately after opening.

#### 4. The Alpine script could not be included twice

The installment script declared `let installmentMap` at the top level. If a theme customisation included the script a second time, the browser threw a redeclaration error, the Alpine component was never registered, and the calculator arrow did nothing.


### What's Fixed

#### Admin design setting

The design is read from **Stores → Configuration → Sales → Payment Methods → Leanpay Installment price → Installment Widget Design** for every render: the product page, price change updates, and Hyvä Checkout. The hardcoded `narrow` argument has been removed from the product page layout.

An `installment_design` layout argument on `product.price.installment_price` still overrides the admin setting, so existing theme overrides keep working.

#### Stable widget key

`wire:key` is now derived from the rendered data (installment plans, amount, design, lowest price and visibility). A Magewire re-render with unchanged data keeps the calculator state, while a change in amount or plans still replaces the widget.

#### Scoped Alpine script

The installment script is wrapped in an immediately invoked function, so including it more than once no longer throws.

#### Compatibility guard

When paired with a payment module that predates the design setting, the widget falls back to the Default design instead of failing the page render. The composer constraint (`>=0.17.0`, see above) already refuses the broken combination; the runtime guard covers installations that manage these modules as git submodules.


### Technical Details

#### Affected Components

- `view/frontend/templates/pricing/render/installment.phtml` - design falls back to the admin setting, with a guard for older payment module versions; deterministic `wire:key`; plans JSON computed once
- `view/frontend/templates/pricing/render/js/installment.phtml` - script wrapped in an IIFE
- `view/frontend/layout/hyva_catalog_product_view.xml` - removed the hardcoded `installment_design` argument

#### Upgrade Notes

- **The product page widget changes from Narrow to Default.** Stores that want the compact widget must select Narrow in admin after upgrading.
- Hyvä Checkout keeps the Default design unless Narrow is selected.
- Stores that added a theme layout override only to switch the design can remove it and use the admin setting instead.
- Run `bin/magento cache:flush` after upgrading. No Tailwind rebuild is needed for this release; both designs use the same classes as before.


### Compatibility

- Backward compatible; existing `installment_design` layout overrides keep working
- No changes to calculated amounts or the calculator content
- Degrades safely against payment module versions older than 0.17.0


### Testing Recommendations

1. Admin design set to Default: product page shows the full widget; the arrow opens the calculator below it on desktop
2. Admin design set to Narrow: product page shows the compact widget; the arrow opens a centred modal on desktop and a bottom sheet on mobile
3. Narrow design, change a configurable or custom option that changes the price: the widget updates its amount and stays narrow
4. Hyvä Checkout with Leanpay selected: the arrow opens the calculator; changing the shipping method refreshes the widget; the calculator opens again afterwards
5. Theme layout override setting `installment_design` to `narrow` with the admin setting on Default: the product page stays narrow
6. No console errors on the product page, category page or checkout
7. Pair deliberately with a payment module older than 0.17.0: the product page renders with the Default design and no fatal error
